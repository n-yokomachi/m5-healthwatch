# HealthWatch（StopWatch × AgentCore）設計書

## 目的

AWSのアドベントカレンダーの記事のために検証用のプロダクトを作る。カレンダーの条件はAWSに関連することで、AIも使う。

利用者はスマホを開かずに声だけでその日の運動の日課を済ませる。StopWatchを床や机に置くか手に持って、床でできる自重の種目とエアロバイクをこなす。記事の主役はAmazon Bedrock AgentCoreで、AgentCore Runtime上のエージェントがその日のメニューを組んで声と画面で案内する。記事ではRuntimeに加えてObservabilityの使いどころも見せる。まず最小の構成で一連の流れを動かす。

## ゴール

- ランチャーの「HealthWatch」から起動すると、アプリが声と画面で今日鍛える部位を提案する
- エージェントは前回のメニューを見て部位を提案し、返事に応じてメニューを組む
- メニューを読み上げて画面に出し、青ボタンでスタートすると種目ごとに回数か経過時間を出す
- 回数の数字・スタート・完了などの決まった言葉を音声で読み上げ、完了を音と振動で知らせる
- 実施したメニューをDynamoDBに保存する

## 対象外

- 普段のストップウォッチ機能。ランチャーにある既存の`app_stopwatch`をそのまま使う
- 体重の記録。デモで体重が画面と声に出ないように、体重は聞かず保存もしない
- 血圧・血糖値の計測と、それに基づく運動の可否の判定
- 保存先の作り込み。検証用なのでDynamoDBの1テーブルで足りる範囲にとどめる

## 失敗とみなす状態

- 器具を使う種目をAIが出し、それがそのまま画面と声に出る
- 運動中の回数の読み上げがネットワークの遅れで途切れたりずれたりする
- オーナーの体重や健康の前提が公開リポジトリのコードやドキュメントに入る

## 制約

- 機器はM5Stack StopWatch（ESP32-S3、466×466の円形AMOLED、マイク、スピーカー、黄・青の物理ボタン、振動モーター、PSRAM 8MB、フラッシュ16MB）
- フラッシュのアプリ領域は`ota_0`（ランチャー）と`ota_1`（HealthWatch）の2つで空きがない。パーティションは作り直さない
- このリポジトリはMITライセンスで公開している
- 検証中のモデルの料金を抑える
- AgentCoreのCLIは公式の`@aws/agentcore`（npm）を使う。旧Pythonのスターターツールキットは使わない
- 対応言語は日本語。Nova 2 SonicとNova 2.5 SonicはAWSの公式資料で日本語対応を確認できなかったので使わない

## 決まっている構成

```
StopWatch（ota_1: HealthWatch）                    AWS
+--------------------------------+  HTTPS   +------------------------------------------+
| 黄ボタンを押しながら話す        | -------> | AgentCore Runtime（Strandsのエージェント） |
| 16kHzのPCMを送る                |          |  Transcribe（文字起こし）                  |
| 返事のPCMを再生し文を画面に出す | <------- |  Nova 2 Lite（Bedrock、メニューを組む）    |
| 回数・決まった言葉は内蔵の音声  |          |  Polly（16kHzのPCMで読み上げ）             |
+--------------------------------+          |  DynamoDB（メニューの履歴）                |
                                            +------------------------------------------+
```

使うAgentCoreの機能はRuntimeとObservabilityの2つ。会話の記憶はレイテンシーを増やさないために持たせず、エージェントが読むのはDynamoDBのメニューの履歴だけにする。

### 起動

- ランチャー（`ota_0`、`menu/`）に「HealthWatch」のアプリを追加する。開くと起動先を`ota_1`に切り替えて再起動する
- `ota_1`のアプリ（`firmware/`）は起動するとHealthWatchとして始まる

### 声の扱い

- 入力: 黄ボタンを押している間だけ16kHzで録音し、エージェントに送る。文字起こしはエージェント側でAmazon Transcribeを使う
- 出力: エージェントは返事の文と、Pollyで合成した16kHz・16bit・モノラルのPCMを返す。StopWatchはPCMを`M5.Speaker`で鳴らし、同じ文を画面に出す
- マイクとスピーカーは同じI2Sの線を使うので、録音と再生を切り替える
- 回数の数字（1から50まで。50を超えた分は数字を読み上げない）、「スタート」「完了」「ややきつくして」「楽にして」など運動中の決まった言葉は、あらかじめPollyで作り、フォント（`font_noto.h`）と同じく`const`配列として`ota_1`のファームウェアに埋め込む。運動中はネットワークを使わずに鳴らす。16kHz・16bitで1秒32KBなので、数字30個と決まった言葉数個で1MB弱になる。`ota_1`は4.9MBなので、ビルドして空きを確認する

### メニューの組み方

- エージェントはNova 2 Liteを使い、DynamoDBから前回のメニューを読んで、今日鍛える部位を提案する
- 利用者の返事に応じて、種目と回数・時間をその都度組む
- 部位の提案は毎回挟む。メニューの画面でも黄ボタンで話せば組み直す（「もっと軽く」など）
- 履歴が空の初回は前回のメニューなしで提案する。デモ用の過去のデータは入れない
- 回数・時間・周回数の上限は設けず、AIに任せる
- 回数・時間・周回数は、その部位の前回のメニューがあれば前回と同じにする。利用者が「もっといける」と言えば少しだけ増やす。増やしたメニューを最後までやると保存され、次の回はそれが前回になる
- その部位を一度もやっていなければ、種目の一覧の設定ファイルに書いた目安（種目ごとの回数や時間と、周回数）で組む。目安は上限ではない
- 使ってよい種目の一覧は設定ファイルに書く。設定ファイルはリポジトリに入れず、例のファイルだけを公開する
- エージェントはメニューを決まった形のデータ（種目名、回数か時間、周回数、左右の有無など）で返す。コード側で一覧にない種目を外してから使う
- メニューは「周回する種目」と、周回がすべて終わった後に1回だけやる「最後の種目」（なくてもよい）に分けられる。エアロバイクのような種目を筋トレの周回の後にまとめてやる組み方に使う
- 「最後の種目」だけのメニューも組める。そのときも周回数は1とし、画面と声では周回数と「最後に」を出さない
- 最初の返事は、部位の提案の1文の後に、次に話すことの案内（「よければ『メニューを出して』と言ってね。ほかの部位にしたいときは、その部位を言ってね。」）を続ける。案内はモデルに書かせず、毎回同じ文にする
- 器具は使わない。種目は床でできる自重の種目とエアロバイク
- 強さの目安は「ややきつい」（会話ができる程度）として、エージェントのプロンプトに書く

### 画面と操作

画面の詳しい仕様は`docs/spec/ui.md`にある。黒い背景・白い目・利用者の言葉は水色にする。少し離れて見る前提で数字を大きくする。画面の文字は種目名・部位・回数や時間・エージェントの返事と聞き取った言葉だけにし、状態と操作はアイコンで示す。青ボタンは青い丸（スタートは再生の印、次へは矢印）、黄ボタンは黄色い丸（話すはマイク、やり直しは円い矢印）で表す。

| 画面 | 内容 |
|---|---|
| 部位の提案 | 小さな目、エージェントの提案、利用者の返事、黄色いマイクのキー。決まった案内の文は声だけで読む |
| メニュー | 部位と繰り返しの印と「×周回数」、種目と回数の一覧、最後の種目の前の区切り線と旗の印、青い再生のキー |
| 回数の種目 | 周回の点の列、種目名、大きな回数と目標の回数、矢印と次の種目（最後は旗の印）、外周に種目の進み具合の輪 |
| 種目の完了 | 輪が2回光って太く残り、数字が消えてチェックが描かれ、粒が外へ広がる。その後は種目名、チェック、青い矢印のキー |
| 次の種目の準備 | 周回の点の列と何種目目か、下向きの印、次の種目名と回数、青い再生のキー |
| 時間の種目 | 種目名、強さの区間（ややきついは炎、楽は波の印）と何本目か、大きな経過時間、矢印と次の区間の印と残り時間、外周の輪 |
| 完了 | いつもの目、部位と周回数、時計の印と合計時間 |

| 入力 | 動作 |
|---|---|
| 黄ボタンを押している間 | 録音してエージェントに送る。部位の提案とメニューの画面で使える |
| 青ボタンのタップ | メニューの画面と次の種目の準備の画面でスタートする。種目の完了の画面では次の種目の準備の画面に進む |
| 青ボタンの長押し | どの画面でも初期画面に戻り、会話を最初からやり直す。運動中なら保存しない |
| 黄ボタンと青ボタンの同時長押し | HealthWatchを終えてランチャーに戻る。録音中なら送らずに捨てる |

- 回数の種目は一定の間隔で回数が1つずつ進み、数字を内蔵の音声で読み上げる
- 1つの種目が終わったら種目の完了の画面で止まり、青ボタンで次の種目の準備の画面に進む。種目が変わるたびに体勢を変えるので、青ボタンでもう一度スタートするまで数え始めない
- 左右のある種目はコード側で「〇〇（右）」と「〇〇（左）」の2つの種目に展開し、普通の回数の種目として扱う。左右の間も次の種目の準備の画面で止まる
- 周回が変わるときは次の種目の準備の画面で止まる。休憩の時間は数えない
- 時間の種目（エアロバイクなど）はストップウォッチのように経過時間を出す。強さの区間は「ややきつい」と「楽」の2段階で、メニューのデータに区間の並び（段階と秒数）を持たせる。エージェントは繰り返す区間の並びと合計の分数を渡してもよく、コード側で並びを繰り返して合計の分数まで埋める。区間が変わるときは「ややきつくして」「楽にして」の決まった言葉を内蔵の音声で読み上げる。エアロバイクの負荷の目盛りの数字は扱わない。最後の区間が終わったら音で知らせて種目の完了の画面に進む
- すべて終わったら音と振動で知らせて完了の画面を出し、実施したメニューをDynamoDBに保存する
- 一時停止は設けない。運動の途中で青ボタンの長押しで初期画面に戻ったら、その回のメニューは保存しない
- 起動したら目と考え中の点を出し、エージェントの提案が届いたら置き換える。考え中も目は待機中と同じようにあちこちを見てまばたきする

### データ

- DynamoDBに1テーブルを作り、実施したメニューを保存する。同じ日に2回運動したら両方残し、「前回」は最後に保存したものを指す。エージェントには前回のメニューと、部位ごとの最後のメニューを渡す

## 公開する成果物

読者が自分の環境で再現できるように、READMEにAWS側のデプロイの手順とStopWatchへの書き込みの手順を追加する。種目の一覧の設定は、利用者の健康の前提を含まない例のファイルだけをリポジトリに入れる。

## 脅威モデル

### データの流れ

```
[StopWatch] --HTTPS(JWT)--> [AgentCore Runtime] --IAMロール--> [Transcribe / Bedrock / Polly / DynamoDB]
     ^                                |
     +-------- 返事の文とPCM ---------+
```

信頼の境界は2つある。StopWatchとAgentCore Runtimeの間（インターネット）と、Runtimeと各AWSサービスの間（IAM）。

### OWASP API Security Top 10 で確認する点

| 項目 | 対策 |
|---|---|
| API2 認証の不備 | Runtimeのインバウンド認証を有効にし、StopWatchは認証情報なしで呼べないようにする。StopWatchが持つ秘密の値はビルド時に`.env`から埋め込み、リポジトリに入れない |
| API4 リソース消費の制限なし | 録音は20秒で打ち切る。Bedrock・Transcribe・Pollyの呼び出し回数に気づけるよう、料金のアラームを設定する |
| API3 / API6 過剰なデータの公開・業務フローの悪用 | エージェントのツールはこのアプリのメニューの読み書きだけにする。DynamoDBへの権限はこのテーブルだけに絞る |
| API8 設定の不備 | RuntimeのIAMロールは使うモデルID・テーブル・Polly・Transcribeに必要な最小の権限だけにする |
| API10 外部APIの安全でない利用 | AIが返したメニューはコード側で一覧にない種目を外してから使う |

StopWatchの秘密の値は機器を物理的に持たれると取り出せる。検証用で利用者は1人なので、その場合は値を作り直して対応する。

## Observability

AgentCore Observabilityは1回の呼び出しのトレースを見るために使う。Transcribe・Nova 2 Lite・Pollyのそれぞれにかかった時間、エージェントが呼んだツール、使ったトークン数を確認し、話してから返事が鳴るまでが遅いときの原因の切り分けと、記事で中の動きを見せる画面に使う。ダッシュボードや独自の指標は作らず、CloudWatchに標準で出るトレースを見る。有効にするための設定は実装の前に公式ドキュメントで確認する。

## 作り手に任せる点

- StopWatchからRuntimeへの認証の方式（JWTを出す仕組みの選択）と、ESP32からの呼び出し方。実装前にAgentCoreの公式ドキュメントで方式と制限を確認する
- 音声と返事をやり取りする形式（HTTPの本文の形、PCMの送り方）と、Transcribeをストリーミングで使うかどうか
- 回数を数える間隔の秒数の既定値（設定で変えられるようにする）
- Pollyの音声からファームウェアに埋め込む配列を作る手順
- AWSのリソースの作り方（`@aws/agentcore`とCDKの分担）
- 設定ファイルの形式と置き場所
- DynamoDBのキーの設計
